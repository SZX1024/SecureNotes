# Cryptographic format

Frozen by requirements §6 and implemented in `packages/shared/src/crypto/format.ts`.
Everything here is **versioned**: a change means a new `crypto_version` and a reader that
can still open older objects, never a silent reinterpretation of existing ciphertext.

## Primitives

| Purpose         | Primitive                             |
| --------------- | ------------------------------------- |
| Data encryption | AES-256-GCM                           |
| Key derivation  | HKDF-SHA-256                          |
| Integrity       | AES-GCM authentication tag (128 bit)  |
| Auxiliary hash  | SHA-256 (cache integrity, dedup only) |

No other algorithm is permitted for data at rest or in transit to the server.

## Envelope

Every encrypted object, in D1 or in R2, carries:

```jsonc
{
  "crypto_version": 1, // envelope format version
  "key_version": 1, // which DEK generation encrypted this object
  "alg": "AES-256-GCM",
  "iv": "<base64, 12 bytes>", // fresh random IV per encryption, never reused
  "ciphertext": "<base64>", // ciphertext || 16-byte GCM tag
}
```

Rules:

- A fresh random 96-bit IV is generated for **every** encryption under a given key.
  Nothing is ever derived from a counter that could repeat after a restore.
- `key_version` is part of the object, not of the storage location, so a rotation can
  proceed object by object and be resumed.
- The AAD is authenticated but not stored in plaintext with the object; it is
  reconstructed deterministically at decryption time.

## AAD

```text
SecureNotes/v1|object_type|object_id|revision|key_version|crypto_version
```

- Field order, prefix and separators are fixed.
- `object_id` must match `[A-Za-z0-9_-]{1,64}`; a value containing `|` is rejected, so a
  crafted identifier can never shift the meaning of the following fields.
- `revision`, `key_version` and `crypto_version` must be safe integers in range.
- The same builder is used when encrypting and decrypting: an object moved to a different
  id, a stale revision or a downgraded `key_version` fails authentication instead of
  decrypting into the wrong slot.

Binding `object_type + object_id + revision + key_version + crypto_version` prevents
cross-object substitution (for example replaying one note's ciphertext as another's
revision).

## Key hierarchy

```text
username + TOTP secret + fixed application context (KDF_CONTEXT) + per-account KDF salt
                                    |
                              HKDF-SHA-256
                                    |
                                   KEK            (never stored)
                                    |
                              Wrapped DEK          (stored: D1 + IndexedDB)
                                    |
                                   DEK            (memory only, non-extractable where possible)
                                    |
                              AES-256-GCM
                                    |
                        encrypted notes / folders / tags / attachments
```

- The 6-digit current TOTP code is **never** a KDF input (requirements §6); only the
  long-lived TOTP secret is.
- The KDF salt is random per account and may be stored in D1.
- The TOTP secret is generated by the server, shown once as a QR code, and not exportable
  through the UI. After a successful authentication the client receives it over HTTPS to
  derive the KEK; it lives in memory only and is never persisted or logged. This is the
  direct consequence of the frozen hierarchy and is covered by the accepted risk in
  [the threat model](./threat-model.md) and requirements §25.

## Recovery path

Each of the 10 recovery codes has an independent wrapping:

```text
Recovery Code -> HKDF(RECOVERY_KDF_CONTEXT, per-code salt) -> Recovery KEK
              -> AES-256-GCM wrap of the DEK -> Recovery-Wrapped DEK
```

- Codes are single-use and stored server-side only as verification hashes plus the opaque
  recovery-wrapped DEK. Plaintext codes never reach the server, logs, URLs or analytics.
- A recovery login yields the DEK, revokes all other sessions (keeping the current one)
  and prompts the user to rebind TOTP.

## Offline / App Lock unlock

Requirements §7 forbids persisting a plaintext DEK but mandates full offline
functionality. The client therefore stores, in IndexedDB:

- the KEK-wrapped DEK (the normal path, needs username + TOTP secret), and
- a DEK wrapped by a **non-extractable** device `CryptoKey` generated locally.

App Lock (40 minutes) is enforced in the client; local unlock uses the device key so
offline editing works without the network, while online authentication and synchronisation
still require TOTP. WebAuthn/Passkey can be layered on top later as an optional local
factor.

## TOTP rebind and migration

Approved semantics (see [decisions](./decisions.md), ADR-004): because the DEK is what
encrypts data and only the KEK changes, a rebind **re-wraps** the DEK and all 10
recovery wrappings and bumps `key_version`; bulk re-encryption of note/attachment
ciphertext is not required to achieve the security goal.

Procedure:

1. Authenticate with the current TOTP.
2. Generate a new TOTP secret; display the new QR code.
3. Verify a code from the new secret.
4. Only then invalidate the old secret.
5. Revoke all existing sessions.
6. Derive the new KEK, re-wrap the DEK, re-wrap all recovery codes, bump `key_version`.
7. Refresh local key material and resume editing.

Constraints: rebinding is refused while unsynced offline modifications exist; normal
editing is disabled during migration; the migration is resumable and the previous KEK
wrapping is only deleted after the new one is confirmed, so an interruption can always
roll back. Data preservation outranks migration speed.

## Versioning policy

- `crypto_version` describes the **envelope/AAD layout**.
- `key_version` describes the **DEK generation**.
- Readers must accept every version they still claim to support and must fail closed on
  unknown values rather than guessing.
