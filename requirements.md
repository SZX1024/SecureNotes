# Secure Memo Web App — Requirements Specification

> Status: Requirements frozen for implementation planning  
> Target: Coding/engineering agent  
> Scope: Personal, single-user, security-oriented memo/PWA web application  
> Primary platform: Cloudflare Workers + D1 + R2  
> Client: Modern browser / PWA  
> Authentication: Self-built username + TOTP  
> Encryption: Client-side encryption

## 1. Product Goals

Build a personal memo application with strong client-side encryption, local-first/offline-first operation, full offline viewing/editing, automatic incremental synchronization, explicit conflict detection/manual resolution, Markdown + WYSIWYG editing, folders/tags/notes, encrypted image attachments in R2, PWA support, self-built username+TOTP authentication, one-time Recovery Codes, session/device management, 30-day security audit logs, and no third-party analytics.

The application must remain compatible with open-source publication: security must rely on secret key material and correct cryptographic implementation rather than hidden source code or algorithms.

Threat model: ordinary Internet attacks, including brute force, XSS, CSRF, SQL injection, session hijacking, broken authorization, malicious uploads, replay, and sync conflicts. Nation-state/extreme full-infrastructure compromise is outside the accepted threat model.

## 2. Deployment Architecture

Required infrastructure:

- User-owned domain and Cloudflare DNS.
- Cloudflare Workers.
- Cloudflare D1.
- Cloudflare R2.
- Browser Web Crypto API.
- IndexedDB.
- Service Worker/PWA.

Do not require Cloudflare Access, VPS, self-hosted backend, native applications, or third-party analytics.

Architecture:

```text
Internet
  -> Cloudflare DNS / HTTPS
  -> Cloudflare Worker
       -> Authentication / Session
       -> REST API /api/v1/*
       -> Validation / Authorization
       -> D1
       -> R2
  -> Browser
       -> WYSIWYG Markdown editor
       -> Client-side encryption/decryption
       -> IndexedDB
       -> Sync Queue
       -> Search index
       -> Service Worker
```

The browser is the trusted plaintext-processing zone. Worker/D1/R2 are semi-trusted/untrusted with respect to note plaintext.

## 3. Account and Authentication

- Exactly one application account.
- Username is configured during first-run initialization and is immutable afterward.
- Initial TOTP Secret is randomly generated by the server and shown as a QR code.
- Generate 10 Recovery Codes, each 32 random characters.
- Recovery Codes are shown only once.
- TOTP Secret cannot be exported through the Web UI.
- Login uses username + current TOTP.
- Recovery login uses username + one Recovery Code.
- No permanent account lockout.
- Failed authentication uses exponential progressive backoff with a cap.
- Rate limiting applies by IP, account, and global endpoint.

### Recovery Codes

Recovery Codes are high-value data-recovery credentials. They are single-use, stored server-side only as secure verification representations/hashes, never logged, never placed in URLs, and never sent to analytics.

A Recovery Code can recover the user's DEK. After Recovery Code login, the current Session may continue, but the user is prompted to reconfigure TOTP. Using a Recovery Code revokes other Sessions while retaining the current recovery Session.

### TOTP rebind

1. Authenticate with current TOTP.
2. Generate a new TOTP Secret.
3. Display new QR.
4. Verify the new TOTP.
5. Only after successful verification invalidate the old TOTP.
6. Revoke all existing Sessions.
7. Re-encrypt/migrate all data using the new key hierarchy.
8. Refresh Recovery-key wrapping.

TOTP changes are prohibited while unsynced offline modifications exist. During migration normal editing is disabled. Migration must be resumable; if it cannot resume, rollback must be possible. Data preservation has priority over migration speed.

## 4. Sessions

- Session ID: UUIDv7.
- Session token: 256-bit cryptographically random value.
- Server stores only SHA-256(token).
- Cookie name: `session`.
- Cookie: `HttpOnly; Secure; SameSite=Strict; Path=/`.
- Normal inactivity policy: 40 minutes.
- Sliding expiration.
- Remember-device maximum lifetime: 30 days and never bypasses TOTP.
- Maximum 5 active/stored Sessions.
- Multiple concurrent Sessions are allowed.
- Session/device UI shows last activity, browser+OS, truncated IP, current-device marker, and editable device name.
- Full User-Agent and full IP are not shown.
- Individual revoke and revoke-all are required.
- Revoking current Session immediately logs the user out.
- Revoke-all includes the current Session.
- A device discovering that its Session was revoked must delete local cache and Wrapped Key/local key material and return to authentication.

Implementation may avoid a D1 write on literally every request by applying a small internal refresh/write threshold while preserving the required sliding-expiration semantics.

## 5. Security Audit Logs

Use a dedicated `audit_logs` table.

Required events:

- Successful login.
- Failed login.
- Session creation.
- Session revoke.
- Revoke-all.
- TOTP change.
- Recovery Code use.
- Data operation type and time.
- Other security-sensitive account events as needed.

Retention is exactly 30 days with automatic cleanup. Users cannot manually clear logs.

Never log note plaintext, note title/body, TOTP Secret, Recovery Codes, encryption keys, or other plaintext secrets.

Audit IP is truncated. User-Agent is represented only as browser/system category. Failure reason is category-only. Session ID is logged. Sensitive audit fields are encrypted; non-sensitive metadata may remain in D1 plaintext.

## 6. Cryptographic Architecture

Use:

- AES-256-GCM for data encryption.
- HKDF-SHA-256 for KDF.
- Browser Web Crypto API.

### Key hierarchy

```text
Username + TOTP Secret + fixed application context + account KDF Salt
                              |
                              v
                         HKDF-SHA-256
                              |
                              v
                    KEK (Key Encryption Key)
                              |
                              v
                         Wrapped DEK
                              |
                              v
                    DEK (Data Encryption Key)
                              |
                              v
                         AES-256-GCM
                              |
                              v
                     Encrypted application data
```

The DEK performs actual data encryption. The KEK wraps/protects the DEK.

The KDF Salt is random per account and may be stored in D1. Never use the six-digit current TOTP code as KDF input.

### Recovery key path

Each Recovery Code gets independent recovery wrapping:

```text
Recovery Code -> recovery derivation -> Recovery KEK -> Recovery-Wrapped DEK -> DEK
```

The server need not store Recovery Code plaintext.

### Encrypted object format

Every encrypted object must carry at least:

- `crypto_version`
- `key_version`
- algorithm identifier
- random IV
- ciphertext/authentication tag

AES-GCM uses a fresh random 96-bit IV for every encryption under the same key. Never reuse an IV.

Use AAD to bind relevant metadata such as:

```text
object_type + object_id + revision + key_version + crypto_version
```

AAD must be reconstructed deterministically and verified during decryption.

AES-GCM authentication is the primary integrity mechanism. SHA-256 may additionally be used for cache integrity, corruption detection, or deduplication-related auxiliary logic.

### TOTP key migration

All plaintext re-encryption happens client-side. Worker never receives note plaintext for migration.

## 7. Local Key Storage and Offline Unlock

IndexedDB stores encrypted data and protected key material. Use Web Crypto non-extractable `CryptoKey` where technically appropriate and persist a Wrapped DEK rather than a plaintext DEK string.

Full offline viewing/editing is required, including notes, folders, tags, and image operations.

WebAuthn/Passkey is optional for local-device authentication.

App Lock: 40 minutes. On application/page close, clear in-memory plaintext and DEK/key material where possible. Persist only protected/encrypted material.

## 8. IndexedDB and Cache

IndexedDB primarily stores:

- Encrypted notes.
- Required encrypted metadata.
- Encrypted attachment/cache data.
- Wrapped Key.
- Sync Queue.
- Revision/synchronization metadata.

Do not permanently cache everything unnecessarily.

When storage pressure occurs, oldest already-synced data may be evicted. Synced attachments may be evicted and re-downloaded. Unsynced data must never be automatically evicted.

Browser site-data clearing may destroy local data, including unsynced changes; no additional warning is required.

## 9. Data Model

Core D1 tables:

```text
users
sessions
recovery_codes
totp_config
folders
tags
notes
note_revisions
note_tags
attachments
note_attachments
sync_changes
audit_logs
```

### Users

Store account identity/status, immutable username, timestamps, random KDF Salt, and relevant key/version metadata.

### Folders

- `id`
- `user_id`
- `parent_id`
- encrypted name/metadata
- timestamps/deletion state

Maximum depth: 10. Structural relationships may be visible to the server; names must be encrypted.

Deleting a folder moves it and contained notes to the recycle bin while preserving IDs and subtree relationships.

### Tags

Tags are flat. Store tag metadata encrypted. Use a separate `note_tags` many-to-many table. Maximum 10 tags per note.

Deleting a tag removes relationships only. Favorites use the reusable tag mechanism rather than a separate Favorites system.

### Notes

Each note:

- belongs to exactly one folder;
- has an ID;
- has current revision;
- has creation timestamp;
- has deletion state;
- has sync state/version;
- stores encrypted Markdown payload.

Title is part of encrypted Markdown, not a separate field.

Server may see note ID, folder relationship, creation timestamp, size, structural/sync metadata. Server must not see title/body, folder names, tag names, or original attachment filenames.

### Revisions

Each note has a monotonically increasing revision starting at 1. Store revision ID, note ID, parent revision ID, revision number, encrypted payload, and creation timestamp.

Keep current revision plus at most 10 historical versions. Remove oldest history automatically when the limit is exceeded. Deleting a historical version is permanent. Permanent note deletion removes current and historical data.

### Attachments

Only images. Maximum 20 MB/image. Preserve original resolution, animated GIF, and dynamic WebP. No automatic compression. Browser-common formats are supported.

R2 object keys use random IDs such as:

```text
attachments/{random-id}
```

Original filenames are encrypted.

Attachments are independent entities because one image can be referenced by multiple notes. Use `attachments` + `note_attachments` and maintain a reference count.

When reference count reaches zero, enqueue asynchronous R2 deletion. Do not block the user operation on immediate R2 deletion.

Structure:

A note has exactly one folder and up to 10 tags.

Sorting:

- Recently modified.
- Creation time.

Required:

- Recent opened list.
- Global full-text search.
- Command palette.
- Global search shortcut.
- Full keyboard shortcuts.

## 11. Search

Search is client-side after decryption. Do not provide server-side plaintext full-text search.

Search fields:

- Title.
- Body.
- Tags.
- Folder names.
- Attachment information.

Support exact and fuzzy search with result highlighting.

Build the search index in memory after unlock; do not persist a plaintext search index.

## 12. Editor and Markdown

Markdown is the canonical storage format. WYSIWYG is the default editor, with a Markdown source mode.

Mobile defaults to WYSIWYG.

Required Markdown features:

- Code blocks.
- Syntax highlighting.
- LaTeX/KaTeX.
- Markdown tables.
- Task lists.
- Mermaid.
- External links.
- External images.
- SVG.
- Safe HTML.
- iframe/video embeds.

Unknown Markdown extensions must be preserved as raw Markdown rather than silently destroyed.

### HTML and CSS

Allow safe HTML. Use a mature Sanitizer library plus browser-native sanitization capabilities where appropriate and custom rules.

Prohibit `<script>` and all inline event-handler attributes such as `onclick`, `onerror`, and `onload`.

CSS `style` is allowed only after strict filtering/sanitization.

### SVG

SVG is allowed but must be strictly sanitized. At minimum prohibit script, event handlers, dangerous external resource references, and other active-content mechanisms.

### Mermaid

Client-side rendering only. Generated SVG must pass through the SVG sanitizer before DOM insertion.

```text
Markdown -> Mermaid -> SVG -> SVG Sanitizer -> DOM
```

### KaTeX

Only use KaTeX-generated safe HTML output. Do not allow arbitrary HTML inside formulas.

### Links

Only allow `http://` and `https://` schemes. External links open in a new window/tab and receive:

```text
rel="noopener noreferrer"
```

Do not automatically convert plain-text URLs into links.

### External images

Allow arbitrary HTTPS external image URLs, subject to safe resource/CSP handling.

### iframe/video

Arbitrary HTTPS iframe/video embeds are permitted by product requirements. Embedded content must be isolated from application privileges. Use restrictive sandboxing where compatible and ensure it cannot access application DOM/storage. CSP must explicitly account for iframe behavior.

### Paste/drop

Rich-text webpage paste prompts the user for handling. Any HTML path must be sanitized. Provide a safe rich-text conversion path and plain-text path.

Clipboard image paste immediately creates an attachment and inserts its internal Attachment ID reference.

Drag/drop accepts images only. Files over 20 MB are rejected.

### Image references

Use internal random Attachment IDs, not original filenames. Removing a reference updates reference counting; zero-reference attachments enter asynchronous R2 deletion.

No dedicated Alt-text feature is required.

## 13. CSP and Rendering Security

Use Content Security Policy. Keep it strict while accommodating required HTTPS external images, iframe behavior, Mermaid, and KaTeX.

Never weaken CSP to permit arbitrary script execution.

No third-party analytics/statistics.

## 14. API Security

Use same-origin REST API under:

```text
/api/v1/*
```

Do not enable CORS. API access is same-origin and cookie-based.

Use defense-in-depth CSRF protection:

- CSRF token.
- Strict Origin/Referer validation.
- SameSite=Strict cookie.

State-changing endpoints must enforce appropriate CSRF checks.

Supported request formats:

- `application/json`
- `multipart/form-data` for attachment operations.

Content-Type must be strictly validated.

Each endpoint has a strict HTTP method.

Every endpoint requires schema validation, authorization, body-size limits, field/depth/array limits as appropriate, and resource ownership checks.

All user-controlled SQL values must use parameterized queries.

Use foreign keys and indexes.

Use D1 transactions for multi-record logical operations where practical.

Production API errors must use a stable generic structure and must not expose stack traces, SQL details, or secrets. Development mode may expose diagnostics.

## 16. Synchronization

Local-first incremental synchronization is mandatory.

Client mutation requests include `base_revision`. Server accepts only when current revision equals base revision. Otherwise it creates a conflict instead of silently overwriting.

### Conflict model

For note conflicts retain:

- Base.
- Local.
- Remote.

UI uses a three-column Base / Local / Remote diff.

Provide:

- Keep local.
- Keep remote.
- Manual merge.

Use Markdown three-way merge to assist manual resolution; unresolved sections must remain visible.

Folder movement conflicts enter conflict state. Tag changes use set semantics where safe. Delete-vs-modify is always a conflict.

### IDs

Offline-created notes may use temporary client IDs. Server generates final Note IDs during sync and returns an ID mapping. Local references must be rewritten atomically.

### Queue

Each operation is tracked. Continuous edits to the same note may be compressed during upload, but unsynced intent must not be discarded.

Different notes may sync in parallel; the same note must sync serially.

### Retry

Use exponential backoff. After repeated failure pause automatic retry, preserve the queue, show an error state, and permit `Sync Now`.

Authentication failures trigger reauthentication. Conflicts pause the affected object until resolved.

### Cursor and tombstones

Use server-provided incremental sync cursor.

Deleted objects use tombstones retained for 30 days so long-offline devices can receive deletions.

## 17. Sync UI and Triggers

Required states:

- Synced.
- Pending.
- Syncing.
- Conflict.
- Offline.
- Sync error.
- Authentication required.

Automatic sync occurs:

- Approximately 5 seconds after the user stops editing.
- On application startup.
- On page resume.
- Immediately after network recovery.

Provide manual `Sync Now`.

## 18. Version History

Save historical revisions using a time-based interval rather than every keystroke. Keep at most 10 historical versions. Restoring history should create a new current revision rather than corrupting existing history.

The exact history-save interval is an implementation configuration.

## 19. Recycle Bin and Cleanup

Recycle-bin retention: 30 days.

Deleted notes retain original IDs and encrypted history until permanent deletion. Permanent deletion removes current and historical data.

Deleted folders preserve IDs and subtree relationships. Deleted tags remove relationships only.

Cleanup may remove expired encrypted data and R2 objects asynchronously.

## 20. Export / Import

### Export

- Manual only; no automatic backups.
- Full export only, not selected-note partial export.
- Default/export format: plaintext ZIP with dedicated application structure.
- Temporary export data is automatically cleaned from browser storage after export.
- Remind user to manually back up after 30 days without an export.
- Plaintext exports are outside the application encryption boundary.

### Recovery package

Provide a separate account recovery package. It must not contain plaintext TOTP Secret. It contains only minimum protected key/recovery metadata required by the recovery design. Format must be versioned.

### Import

Import is transactional. Validate the entire archive, records, references, attachment metadata, and cryptographic metadata before commit. Any failure rolls back the entire import.

Duplicate IDs require user choice for merge/remap handling. Implement smart merge rather than unconditional overwrite.

## 21. PWA and Service Worker

Provide an installable PWA with offline application shell and full offline editing/viewing.

Service Worker updates are automatic when safe. If unsynced data exists, delay update until synchronization is safe.

IndexedDB migrations are versioned. Preserve the old database while creating/migrating the new schema; switch only after successful migration. Never destroy the last known-good database before migration succeeds.

Show application version in Settings/About.

## 24. Privacy Boundary

The server may know normal Cloudflare/network metadata such as IP, request time, User-Agent/network information, API path, random object IDs, sizes, creation timestamp, structural relationships, and synchronization/session metadata.

The server must not receive plaintext:

- Note title/body.
- Folder names.
- Tag names.
- Original attachment filenames.
- Search queries/content.

Creation timestamp may remain visible; modification-time privacy should follow the encrypted metadata design.

No third-party analytics/statistics.

## 25. Open Source Security Model

The source code, algorithms, and protocol may be public.

Security must depend on secret material and correct implementation, not obscurity.

An attacker possessing only:

```text
source code + D1 ciphertext + R2 ciphertext
```

without required secret key material must not be able to decrypt note plaintext.

Accepted threat-model boundary: if an attacker fully compromises the Worker runtime and obtains D1, R2, Session secrets, TOTP Secret, and Worker environment secrets, historical data may become decryptable. This is explicitly accepted.

## 26. Replay / Idempotency / Authorization

Sensitive operations use one-time operation IDs/nonces bound to the user/Session and a short lifetime. At minimum apply to TOTP changes and recovery operations.

Design sync, uploads, deletes, and security-sensitive state transitions to be idempotent where practical.

Every authenticated endpoint must verify:

```text
authenticated user
+ resource belongs to user
+ operation is valid for current state
```

Random IDs are identifiers, not authorization.

## 27. Database Integrity

Use foreign keys, appropriate indexes, transactions, and revision-based optimistic locking.

Note update must use an atomic condition equivalent to:

```sql
UPDATE notes
SET ...
WHERE id = ?
  AND revision = ?;
```

If no row is updated because the revision changed, treat it as a conflict.

## 33. Engineering Rules for Coding Agents

1. Do not silently change frozen product requirements.
2. If an implementation constraint conflicts with a requirement, stop and explain the conflict before changing it.
3. Prefer secure defaults.
4. Never log secrets or plaintext notes.
5. Never introduce third-party analytics.
6. Never introduce server-side plaintext note processing without explicit approval.
7. Never use last-write-wins for note conflicts.
8. Never discard unsynced local changes automatically.
9. Never bypass TOTP because a device is remembered.
10. Never treat random IDs as authorization.
11. Never render user-controlled HTML/SVG/Mermaid directly without sanitization.
12. Never allow unsupported URL schemes.
13. Never reuse AES-GCM IVs under the same key.
14. Never persist a plaintext DEK as ordinary data.
15. Use migrations for database schema changes.
16. Keep security-sensitive code isolated and testable.
17. Add tests for every security boundary.
18. Preserve encrypted-data compatibility using explicit crypto/key versions.
19. Prefer same-origin APIs.
20. Keep plaintext and active key material lifetime as short as practical.
